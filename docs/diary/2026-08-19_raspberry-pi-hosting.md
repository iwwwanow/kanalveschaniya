# 2026-08-19 — хостинг на домашнем Raspberry Pi 3B

## Цель

Перенести бота с текущего хоста на домашний Raspberry Pi 3B, попутно разобраться с k3s (осознанное решение — учебный полигон, не только хостинг). Обсуждали GitOps/автодеплой, опциональность хранения треков, и упёрлись в то, что сам Pi не отвечает на попытки его найти в сети.

## Что сделано в коде (готово, закоммичено не было — коммитит юзер сам)

Реализована опциональность обоих способов сохранения медиа — раньше `saveToContent()` вызывался всегда безусловно поверх обязательной заливки в канал. Идея юзера была «использовать Telegram как единственное хранилище» — но в процессе выяснилось, что это уже почти так и работало: повторные запросы того же URL и так раздаются через `forwardMessage` по `channel_message_id` из таблицы `tracks` (`bot/handlers.ts:56-65`), а `CONTENT_DIR` — это была чисто побочная, нигде не читаемая копия.

- `src/config.ts` — добавлены `CACHE_TO_CHANNEL` и `SAVE_TO_CONTENT_DIR` (оба `boolean`, дефолт `true` = текущее поведение). Внизу файла — валидация: если оба `false`, кидаем `Error` при старте (аналогично проверке `BOT_TOKEN`/`CHANNEL_ID`) — медиа обязано осесть хоть где-то, юзер сам это подловил в ревью.
- `src/worker/index.ts` (~224-267) — ветвление:
  - `cacheToChannel=true` — как раньше: заливка в канал, insert в `tracks`, forward пользователю.
  - `cacheToChannel=false` — файл шлётся пользователю напрямую (`sendAudio`/`sendVideo` в `user_id`), в `tracks` ничего не пишется. **Важно:** это отключает дедуп по URL — при следующем запросе того же трека будет повторное скачивание, т.к. `handlers.ts` матчит только по `channel_message_id`. Fallback-lookup по `CONTENT_DIR` для этого случая не делали — юзер сознательно не просил, оставили как есть.
  - `saveToContentDir=true` — как раньше, `saveToContent()` перекладывает файл в `CONTENT_DIR`.
  - `saveToContentDir=false` — временный файл просто `unlink`.
- Схему БД не трогали — `tracks.channel_message_id` остаётся `NOT NULL`, миграция не нужна, т.к. строка в `tracks` пишется только когда канал реально используется.
- `CLAUDE.md` — добавлены обе переменные в таблицу env vars.
- `bun run typecheck` — чисто после обеих правок.

## Инфраструктурная часть — где застряли

### GitOps и динамический IP — не связаны

Ключевое заблуждение на старте: «динамический IP не даст настроить GitOps». Неверно — GitOps pull-based (Flux/ArgoCD/k3s image-automation), агент сидит **внутри** кластера на Pi и сам исходящим соединением опрашивает git/registry, IP-адрес Pi для этого не имеет значения вообще. Дин. IP становится проблемой только для **inbound** сценариев (кто-то стучится К Pi — вебхук, SSH снаружи, kubectl извне) — для них решение стандартное: Tailscale/WireGuard вместо DDNS.

### Обнаружение Pi в сети — не задалось с самого начала

Юзер сидит на Arch (`archlinux.local`, `192.168.0.146`), NetworkManager не используется — стек `iwd` (wifi) + `systemd-networkd`. `nmcli` бинарник есть, но демон не запущен — мой первый совет через `nmcli connection ... shared` был неверным под этот стек, поправился на `systemd-networkd` c `DHCPServer=yes`.

Хронология попыток найти Pi:
1. `ping raspberrypi.local` — не резолвился. Причина оказалась банальной: `avahi-daemon` на ноуте был `inactive` (`systemctl is-active avahi-daemon`). Включили.
2. Заподозрили VPN как причину недоступности — проверили `ip route`: дефолтный маршрут у юзера идёт через `wlan0` (обычный домашний WiFi), а не через `tailscale0`/`tun0` — оба VPN подняты, но не full-tunnel. VPN не был причиной проблемы вообще.
3. `sudo nmap -sn 192.168.0.0/24` (несколько раз, включая после physical replug кабеля в роутер) — стабильно находит только 4 хоста: gateway (TP-Link), `ubuntu-host.local` (чужая машина в сети), IoT-девайс (Smartlabs), сам ноут (`archlinux.local`). **Pi ни разу не появился** — ни один MAC не матчит Raspberry Pi Foundation OUI (`b8:27:eb`, `dc:a6:32`, `e4:5f:01` и т.п.).
4. Пробовали прямое подключение Pi↔ноут по кабелю в обход роутера — начали поднимать `systemd-networkd` DHCP-сервер на `enp0s31f6` (файл `10-pi-direct.network`, приоритет выше дефолтного `20-ethernet.network`), но запись через `sudo tee` уёрлась в интерактивный запрос пароля (Bash-тул не может его ввести) — **файл так и не был создан**, ничего на ноуте не сломано/не оставлено.
5. Нашли в `~/.ssh/config` старую запись `Host rpi / User operator / Hostname 77.51.219.2 / Port 22` — предположительно старый port-forward под прошлый WAN IP, сейчас почти наверняка неактуален (та же проблема дин. IP, с которой всё начиналось), не проверяли — на момент находки Pi не имел выхода в интернет (кабель был выдернут из роутера).

**Вывод сессии: Pi в текущем состоянии не отвечает в сети ни при каком подключении** (ни через роутер, ни напрямую), при этом юзер не помнит, что на нём вообще накручено («может там просто системы нет»). Решили не копать вслепую дальше, а переустановить.

### Переустановка — план

- `rpi-imager` в официальных репах Arch (`extra`), никакого AUR не нужно — юзер уже поставил.
- **Проблема с носителем**: единственная сразу доступная microSD — `/dev/sda`, **1.9GB** (модель `SD/MMC` в `lsblk`). Официальный минимум под Raspberry Pi OS — 8GB. Причём дело не только в весе конкретного образа ОС — k3s + containerd + образы контейнеров всё равно съедят несколько GB независимо от выбора дистрибутива, так что «более лёгкий образ» эту проблему не решает в принципе.
- Решили ставить **DietPi** вместо Raspberry Pi OS — тот же Debian/apt под капотом, легче база, встроенный `dietpi-software` каталог с Docker в одну команду. Всё равно нужен носитель ≥8GB под сам k3s data-dir.
- **USB-boot на Pi 3B**: возможен, но зависит от даты выпуска платы — платы после ~2017 могут иметь OTP-бит USB-boot включённым с завода, более старые требуют одноразового бутстрапа с SD-карты (официальный enabler-образ крошечный — та самая имеющаяся 1.9GB карта отлично для этого подходит как одноразовый инструмент, дальше не нужна).
- **Финальная договорённость по железу** — три отдельных флешки:
  1. Загрузочная — DietPi (USB-boot напрямую, либо через 1.9GB SD как одноразовый бутстрап для OTP-бита).
  2. Под данные k3s (containerd/образы/local-path storage) — монтируется в `/mnt/k3s-data`, k3s ставится с флагом `--data-dir=/mnt/k3s-data` (переносит всё разом).
  3. Под скачивание треков — `/mnt/downloads`, прокидывается в под бота как `hostPath`-volume на место `TMP_DIR`/`CONTENT_DIR`.
  - Названные риски (не блокеры, просто держать в голове): все 4 USB-порта + Ethernet на Pi 3B сидят на одном внутреннем USB2.0-хабе — при параллельной нагрузке на все три флешки + сеть будет общий потолок пропускной способности; плюс три независимые файловые системы = три точки отказа вместо одной.
