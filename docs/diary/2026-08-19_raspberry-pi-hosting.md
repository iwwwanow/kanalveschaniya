# 2026-08-19 — хостинг на домашнем Raspberry Pi 3B

## Цель

Перенести бота с текущего хоста на домашний Raspberry Pi 3B, попутно разобраться с k3s (осознанное решение — учебный полигон, не только хостинг). Обсуждали GitOps/автодеплой, опциональность хранения треков, и упёрлись в то, что сам Pi не отвечает на попытки его найти в сети.

## Что сделано в коде (готово, закоммичено не было — коммитит юзер сам)

Реализована опциональность обоих способов сохранения медиа — раньше `saveToContent()` вызывался всегда безусловно поверх обязательной заливки в канал. Идея юзера была «использовать Telegram как единственное хранилище» — но в процессе выяснилось, что это уже почти так и работало: повторные запросы того же URL и так раздаются через `forwardMessage` по `channel_message_id` из таблицы `tracks` (`bot/handlers.ts:56-65`), а `CONTENT_DIR` — это была чисто побочная, нигде не читаемая копия.

- `src/config.ts` — добавлены `CACHE_TO_CHANNEL` и `SAVE_TO_CONTENT_DIR` (оба `boolean`, дефолт `true` = текущее поведение). Внизу файла — валидация: если оба `false`, кидаем `Error` при старте (аналогично проверке `BOT_TOKEN`/`CHANNEL_ID`) — медиа обязано осесть хоть где-то, юзер сам это подловил в ревью.
- `src/worker/index.ts` (~224-267) — ветвление:
  - `cacheToChannel=true` — как раньше: заливка в канал, insert в `tracks`, forward пользователю.
  - `cacheToChannel=false` — файл шлётся пользователю напрямую (`sendAudio`/`sendVideo` в `user_id`), в `tracks` ничего не пишется. **Важно:** это отключает дедуп по URL — при следующем запросе того же трека будет повторное скачивание, т.к. `handlers.ts` матчит только по `channel_message_id`. Fallback-lookup по `CONTENT_DIR` для этого случая не делали — юзер сознательно не просил, оставили как есть.
  - `saveToContentDir=true` — как раньше, `saveToContent()` перекладывает файл в `CONTENT_DIR`.
  - `saveToContentDir=false` — временный файл просто `unlink`.
- Схему БД не трогали — `tracks.channel_message_id` остаётся `NOT NULL`, миграция не нужна, т.к. строка в `tracks` пишется только когда канал реально используется.
- `CLAUDE.md` — добавлены обе переменные в таблицу env vars.
- `bun run typecheck` — чисто после обеих правок.

## Инфраструктурная часть — где застряли

### GitOps и динамический IP — не связаны

Ключевое заблуждение на старте: «динамический IP не даст настроить GitOps». Неверно — GitOps pull-based (Flux/ArgoCD/k3s image-automation), агент сидит **внутри** кластера на Pi и сам исходящим соединением опрашивает git/registry, IP-адрес Pi для этого не имеет значения вообще. Дин. IP становится проблемой только для **inbound** сценариев (кто-то стучится К Pi — вебхук, SSH снаружи, kubectl извне) — для них решение стандартное: Tailscale/WireGuard вместо DDNS.

### Обнаружение Pi в сети — не задалось с самого начала

Юзер сидит на Arch (`archlinux.local`, `192.168.0.146`), NetworkManager не используется — стек `iwd` (wifi) + `systemd-networkd`. `nmcli` бинарник есть, но демон не запущен — мой первый совет через `nmcli connection ... shared` был неверным под этот стек, поправился на `systemd-networkd` c `DHCPServer=yes`.

Хронология попыток найти Pi:
1. `ping raspberrypi.local` — не резолвился. Причина оказалась банальной: `avahi-daemon` на ноуте был `inactive` (`systemctl is-active avahi-daemon`). Включили.
2. Заподозрили VPN как причину недоступности — проверили `ip route`: дефолтный маршрут у юзера идёт через `wlan0` (обычный домашний WiFi), а не через `tailscale0`/`tun0` — оба VPN подняты, но не full-tunnel. VPN не был причиной проблемы вообще.
3. `sudo nmap -sn 192.168.0.0/24` (несколько раз, включая после physical replug кабеля в роутер) — стабильно находит только 4 хоста: gateway (TP-Link), `ubuntu-host.local` (чужая машина в сети), IoT-девайс (Smartlabs), сам ноут (`archlinux.local`). **Pi ни разу не появился** — ни один MAC не матчит Raspberry Pi Foundation OUI (`b8:27:eb`, `dc:a6:32`, `e4:5f:01` и т.п.).
4. Пробовали прямое подключение Pi↔ноут по кабелю в обход роутера — начали поднимать `systemd-networkd` DHCP-сервер на `enp0s31f6` (файл `10-pi-direct.network`, приоритет выше дефолтного `20-ethernet.network`), но запись через `sudo tee` уёрлась в интерактивный запрос пароля (Bash-тул не может его ввести) — **файл так и не был создан**, ничего на ноуте не сломано/не оставлено.
5. Нашли в `~/.ssh/config` старую запись `Host rpi / User operator / Hostname 77.51.219.2 / Port 22` — предположительно старый port-forward под прошлый WAN IP, сейчас почти наверняка неактуален (та же проблема дин. IP, с которой всё начиналось), не проверяли — на момент находки Pi не имел выхода в интернет (кабель был выдернут из роутера).

**Вывод сессии: Pi в текущем состоянии не отвечает в сети ни при каком подключении** (ни через роутер, ни напрямую), при этом юзер не помнит, что на нём вообще накручено («может там просто системы нет»). Решили не копать вслепую дальше, а переустановить.

### Переустановка — план

- `rpi-imager` в официальных репах Arch (`extra`), никакого AUR не нужно — юзер уже поставил.
- **Проблема с носителем**: единственная сразу доступная microSD — `/dev/sda`, **1.9GB** (модель `SD/MMC` в `lsblk`). Официальный минимум под Raspberry Pi OS — 8GB. Причём дело не только в весе конкретного образа ОС — k3s + containerd + образы контейнеров всё равно съедят несколько GB независимо от выбора дистрибутива, так что «более лёгкий образ» эту проблему не решает в принципе.
- Решили ставить **DietPi** вместо Raspberry Pi OS — тот же Debian/apt под капотом, легче база, встроенный `dietpi-software` каталог с Docker в одну команду. Всё равно нужен носитель ≥8GB под сам k3s data-dir.
- **USB-boot на Pi 3B**: возможен, но зависит от даты выпуска платы — платы после ~2017 могут иметь OTP-бит USB-boot включённым с завода, более старые требуют одноразового бутстрапа с SD-карты (официальный enabler-образ крошечный — та самая имеющаяся 1.9GB карта отлично для этого подходит как одноразовый инструмент, дальше не нужна).
- **Финальная договорённость по железу** — три отдельных флешки:
  1. Загрузочная — DietPi (USB-boot напрямую, либо через 1.9GB SD как одноразовый бутстрап для OTP-бита).
  2. Под данные k3s (containerd/образы/local-path storage) — монтируется в `/mnt/k3s-data`, k3s ставится с флагом `--data-dir=/mnt/k3s-data` (переносит всё разом).
  3. Под скачивание треков — `/mnt/downloads`, прокидывается в под бота как `hostPath`-volume на место `TMP_DIR`/`CONTENT_DIR`.
  - Названные риски (не блокеры, просто держать в голове): все 4 USB-порта + Ethernet на Pi 3B сидят на одном внутреннем USB2.0-хабе — при параллельной нагрузке на все три флешки + сеть будет общий потолок пропускной способности; плюс три независимые файловые системы = три точки отказа вместо одной.

## 2026-08-19, вечер — SD прошита, Pi поднят и найден в сети

### Неожиданная находка перед прошивкой: SD-карта была не пустой

Та самая единственная доступная microSD (`/dev/sda`, 1.9GB) при монтировании оказалась **не пустой** — на ней лежали реальные фото (`DCIM/100MEDIA/*.AVI` и JPG, `PRIVATE/`, `.Trash-1000/`), диск был забит на 100%. Похоже на карту из экшн-камеры (структура `100MEDIA`, `.AVI` в MJPG). Остановился и переспросил юзера, прежде чем стирать — юзер подтвердил, что фото не нужны, стираем.

Побочный квест: юзер параллельно открыл один из видео (`SUNP0001.AVI`) в VLC и упёрся в `Codec not supported: MJPG` — оказалось, что Arch-пакет `vlc` в какой-то момент раздробили на `vlc` + отдельные `vlc-plugin-*` пакеты, и `vlc-plugin-ffmpeg` (даёт `libavcodec_plugin.so`, весь codec-декодинг через ffmpeg) просто не был установлен. Решение: `sudo pacman -S vlc-plugin-ffmpeg` (или `vlc-plugins-extra` для полного набора). Открытый в VLC файл потом мешал `udisksctl unmount` (`device busy`) — нашли через `fuser -vm /dev/sda1`, юзер закрыл VLC сам.

### Прошивка DietPi

- Образ: `DietPi_RPi234-ARMv8-Trixie.img.xz` (64-bit, для BCM2837/BCM2711/BCM2712 — Pi 2 v1.2+/3/4/5) — выбран вместо ARMv6, т.к. CI бота уже собирает arm64-образы, нужно совпадение архитектуры.
- Скачан в scratchpad, проверен по официальному `.sha256` (не `.hash` — на сайте только `.sha256`) — совпал.
- `rpi-imager --cli <img.xz> /dev/sda` — сам умеет распаковывать `.xz` на лету и верифицирует запись после. Писать напрямую в `/dev/sda` нужно **root** (sudo, интерактивный пароль) — агент не может ввести пароль сам, поэтому все привилегированные команды (unmount/dd/partprobe/mount раздела после записи) юзер выполнял сам через `!`-префикс в Claude Code, агент только читал результат.
- После записи `lsblk` без sudo не видел новых разделов, пока не сделали `sudo partprobe /dev/sda` — ядро не перечитало таблицу разделов автоматически после raw-записи через USB-кардридер.
- Итоговые разделы: `sda1` 128M vfat (boot), `sda2` 1000M ext4 (rootfs) — итого ~1.1GB из 1.9GB, +/- как и ожидалось.

### Преднастройка не понадобилась

Проверили `dietpi.txt` на boot-разделе **до** первого запуска — дефолты уже совпадали с тем, что нужно: `AUTO_SETUP_NET_HOSTNAME=DietPi` (юзер сознательно оставил дефолт вместо предложенного `rpi-kanal`), `AUTO_SETUP_NET_ETHERNET_ENABLED=1` + `AUTO_SETUP_NET_WIFI_ENABLED=0` (Ethernet, WiFi выключен), `AUTO_SETUP_SSH_SERVER_INDEX=-1` (Dropbear включён из коробки). Пароль дефолтный `dietpi`/`dietpi`, меняется принудительно при первом логине — штатно, не трогали. **Правка dietpi.txt не понадобилась вообще.**

### Обнаружение в сети — на этот раз быстро

В отличие от прошлой попытки (см. выше — Pi вообще не отвечал), в этот раз всё нашлось за пару минут:
- `ping DietPi.local` / `avahi-resolve` не сработали сразу (mDNS демон на свежесозданном Pi ещё не поднялся к моменту проверки) — не стали ждать, пошли через прямой scan.

- Устройство определилось как **RPi 3 Model B+ (aarch64)**, не просто "Model B" как считалось раньше — стоит поправить это в голове на будущее (не критично для плана, ARMv8-образ всё равно подходит и для B, и для B+).

USB-флешка ≥8GB под `--data-dir` k3s остаётся обязательной, откладывать нельзя.

## 2026-08-19, ночь — SSH-ключ, обе флешки размечены и смонтированы

### SSH по ключу вместо пароля

Юзер сменил дефолтный пароль root на Pi, из-за чего сессионный SSH (Bash-тул) больше не мог логиниться (`Permission denied (publickey,password)`) — интерактивный ввод пароля агенту недоступен. Решение — `ssh-copy-id root@192.168.0.118`, юзер выполнил сам в своём терминале.

Ключ оказался под passphrase, а `ssh-agent` был пуст — сервер принимал публичный ключ (`Server accepts key`), но подпись не проходила (`No more authentication methods to try`). Пробовали `ssh-add` через `!`-префикс в Claude Code — не сработало, `!` не даёт настоящего tty, ssh падает на попытке открыть графический `ssh-askpass`, которого нет (`exec(/usr/lib/ssh/ssh-askpass): No such file or directory`). Юзер запустил `ssh-add ~/.ssh/id_ed25519` в отдельном обычном терминале — ключ подхватился в общий (видимо systemd user-) agent, после этого сессионный SSH заработал без пароля.

### Обнаружение и разметка флешек

`lsblk` на Pi сначала показал только одну флешку (`sda`, JetFlash, 7.6GB, NTFS) — второй не было видно физически, юзер её не воткнул на тот момент. После подключения второй (`sdb`, Netac "OnlyDisk", физически 29GiB) увидели обе.

`sdb` оказалась старой загрузочной флешкой (GPT, один раздел `EFI System` 8GB с содержимым live-Linux — `EFI/`, `live/`, `syslinux/`, `utils/`, `.disk/`, ~1.9GB данных, похоже на SystemRescue или аналог) — 21GB за разделом не были размечены. `sda` — NTFS, смонтировать не удалось сразу (в минимальном образе DietPi не было модуля `ntfs3` загружен по умолчанию, `modprobe ntfs3` есть в `/lib/modules`, но раздел всё равно показывал 0 байт данных — скорее всего пустая).

**USB-питание — реальная проблема, не только гипотетическая (см. риски в начале дневника):** при попытке смонтировать обе флешки одновременно поймали `dmesg`-цикл `hwmon: Undervoltage detected!` / `Voltage normalised` каждые ~12–16 сек, и `sda` физически отвалилась (`USB disconnect`). `vcgencmd get_throttled` показал `0x50005` (биты "under-voltage сейчас" + "throttled сейчас" + оба "occurred"-флага). Юзер вручную вынул `sda`, чтобы посмотреть содержимое на другой машине, воткнул обратно — на момент разметки `throttled` устоялся на `0x50000` (только исторические флаги, без активного undervoltage). Разметку сделали в этом стабильном окне. **Вывод: под сустойнутую нагрузку k3s (одновременная работа обеих флешек + Ethernet) вероятно понадобится powered USB-хаб** — риск был назван ещё в дневном плане, теперь подтверждён эмпирически. Не решали в эту сессию, отложено — если через k3s начнутся необъяснимые обрывы/зависания I/O, первым делом проверять `vcgencmd get_throttled`.

Нейминг точек монтирования обсудили отдельно — юзеру не понравились буквальные `k3s-data`/`downloads`, договорились на более абстрактные:
- **`/mnt/apps`** — под софт/кластер (k3s `--data-dir`, containerd, образы). Раньше в плане назывался `k3s-data`.
- **`/mnt/storage`** — под медиа/файлы в целом (не только downloads — юзер уточнил, что флешка будет использоваться шире). Раньше в плане назывался `downloads`.

Разметка (обе флешки чистые, содержимое не нужно юзеру, стёрто с подтверждения):
```
wipefs -a /dev/sdb && parted -s /dev/sdb mklabel gpt && parted -s /dev/sdb mkpart primary ext4 0% 100%
mkfs.ext4 -F -L apps /dev/sdb1
wipefs -a /dev/sda && parted -s /dev/sda mklabel gpt && parted -s /dev/sda mkpart primary ext4 0% 100%
mkfs.ext4 -F -L storage /dev/sda1
```
После `mkfs.ext4` на `sda` `lsblk` какое-то время продолжал показывать старый `ntfs` без метки — ядро не перечитало таблицу разделов автоматически (тот же паттерн, что при первой прошивке SD), помогло `blockdev --rereadpt /dev/sda && partprobe /dev/sda`.

Смонтировано через `/etc/fstab` по UUID (не по `/dev/sdX` — имена нестабильны при переподключении), с `nofail`, чтобы отсутствие флешки при загрузке не блокировало systemd:
```
UUID=280c2647-8204-46f9-91fa-6656551c38b7  /mnt/apps      ext4  defaults,nofail  0  2
UUID=56faa694-19df-46d1-9ff5-9c979c7dc967  /mnt/storage   ext4  defaults,nofail  0  2
```
`mount -a` — оба смонтированы успешно, `/mnt/apps` 29G/27G свободно, `/mnt/storage` 7.5G/7.1G свободно. Резервная копия `/etc/fstab` до правки — `/etc/fstab.bak` на самом Pi.

## 2026-08-19, продолжение — питание оказалось блокером, k3s отложен

Перед установкой k3s решили ещё раз проверить `vcgencmd get_throttled` — показал `0x50005` (undervoltage **прямо сейчас**, не только исторический флаг, как в конце прошлой сессии). Понаблюдали ~2 минуты (`for i in 1..6; vcgencmd get_throttled; sleep 20`) — значение колебалось между `0x50000` и `0x50005` каждые 20-40 сек, **в полном простое** (DietPi просто висит, флешки смонтированы, ничего не качается, k3s ещё даже не ставился). Юзер подтвердил, что красный PWR LED на Pi периодически мигает — это тот же симптом.

### Разбор причины — БП, не кабель

Прикидка бюджета мощности для Pi 3B+ под реальной нагрузкой (k3s control-plane + containerd + обе USB-флешки):
- Сама плата под нагрузкой всех 4 ядер: до ~1.0–1.3A
- USB-порты (общий полифьюз-лимит на плате) под обеими флешками, особенно при параллельной записи: ~0.3–0.6A
- Итого пиковая потребность: **~1.5–1.9A**, с всплесками к 2A+

БП у юзера — не родной, нестандартный, **5V/1.5A**. Официальный минимум для 3B+ — 2.5A. При 1.5A плата сама на нагрузке съедает почти весь бюджет, на USB-флешки остаётся 0.2–0.5A — этого мало даже для одной флешки под записью, отсюда и просадки уже на простое. Вывод: дело именно в недостаточном токе БП, а не в кабеле (кабель тоже может усугублять, но не первопричина при разрыве бюджета такого масштаба).

**Решение: не ставить k3s на этом БП.** Риск — порча SD-карты (грузимся с неё) или состояния etcd/containerd при обрыве питания посреди записи, потенциально require переустановку с нуля.

### Заказано

Юзер заказал на Ozon новый БП (искали `блок питания Raspberry Pi 3 5.1V 2.5A micro USB`, но по факту заказан **5V/2.4A** — обсудили, что разница с 2.5A в пределах ~4%, некритично, важнее качество стабилизации у конкретного экземпляра) и короткий толстый micro-USB кабель (`кабель micro USB толстый 0.5м для зарядки` — короче и толще штатного, меньше просадка по длине провода). Ожидаемая доставка — на следующий день после заказа.

**Работы по железу (k3s, деплой бота) приостановлены до прихода БП и кабеля.**

## 2026-08-21 — новый БП подключён, питание проверено под нагрузкой

Юзер получил заказанный БП (5V/2.4A) и кабель, подключил к Pi. Проверка через SSH (ключ пришлось заново класть в agent — passphrase, `ssh-add` юзер выполнил сам в отдельном терминале, та же история, что раньше):

- В простое: `vcgencmd get_throttled` = `0x80000` стабильно 2 минуты подряд (проверка каждые 15 сек) — это только бит "soft temperature limit has occurred" (исторический), биты undervoltage (0x1/0x4/0x10000/0x40000) чистые. Раньше на старом БП в простое было `0x50000`/`0x50005` с активным undervoltage.
- Под нагрузкой: параллельная `dd`-запись 500MB на `/mnt/apps` и `/mnt/storage` одновременно + фоновая CPU-нагрузка (`yes > /dev/null`), суммарно ~75 сек — `throttled` не изменился (`0x80000`), `vcgencmd measure_volts core` = 1.2813V, в `dmesg` ни одной строки voltage/throttle/USB disconnect за это время. Раньше именно этот сценарий (параллельная запись на обе флешки) валил `sda` по USB disconnect.

**Вывод: новый БП тянет реальную нагрузку, блокер по питанию снят.** Можно ставить k3s.

### Решения по инструментам (без изменений в коде)

- **k3s, не microk8s** — подтвердили прошлый выбор. microk8s ставится через snap, а на DietPi (не Ubuntu) snapd — источник проблем (нет нормальной AppArmor-интеграции из коробки). k3s — один бинарник без внешних зависимостей, легче по памяти (важно на 1GB RAM у 3B+).
- **Flux, не ArgoCD** — тоже подтвердили прошлый выбор. Оба CNCF graduated / Apache 2.0. ArgoCD тащит веб-UI и прожорливее по ресурсам, Flux — набор контроллеров без UI, легче для Pi.

### mDNS: `ssh pi` вместо IP

Юзер захотел подключаться к Pi по памяти, а не по IP (который к тому же плавает — DHCP, не статика). Раньше (19-го) `DietPi.local` не резолвился — тогда решили, что просто mDNS-демон на свежем Pi не успел подняться, и не стали разбираться. Сегодня разобрались до конца: причина не в тайминге, а в том, что **на DietPi `avahi-daemon` не был установлен вообще** (`dpkg -l | grep avahi` — пусто) — анонсировать mDNS-имя было некому, сколько ни жди.

Исправлено:
- `apt-get install -y avahi-daemon && systemctl enable --now avahi-daemon` на Pi — теперь `DietPi.local` резолвится (`avahi-resolve -n DietPi.local` → `192.168.0.118`).
- Побочная находка: `resolvectl query DietPi.local` без флага по умолчанию возвращает IPv6 link-local (`fe80::...%4`) через mDNS/IPv6, а `ssh root@DietPi.local` с этим адресом падал (`Network is unreachable` / зависание) — похоже на баг работы ssh с zone-id у link-local через systemd-resolved. Обошли через `AddressFamily inet` (форсирует IPv4) — с ним резолвится корректный `192.168.0.118` и ssh отрабатывает чисто.
- Host key при первом подключении к новому имени `DietPi.local` не совпадал с уже известным (known_hosts матчит по имени/IP как отдельным записям) — добавили через `ssh-keyscan -4 -t ed25519 DietPi.local >> ~/.ssh/known_hosts`, сверили, что fingerprint совпадает с уже доверенной записью для `192.168.0.118` (совпал, это тот же хост).
- В `~/.ssh/config.d/personal.conf` (не под stow/git-sync, обычный файл) заменили старую мёртвую запись `Host rpi` (WAN IP `77.51.219.2`, из давнего port-forward, юзер `operator`) на:
  ```
  Host pi
  	User root
  	Hostname DietPi.local
  	AddressFamily inet
  	Port 22
  ```
  Проверено — `ssh pi` подключается. Имя `pi` переживёт смену IP Pi (DHCP), т.к. резолвится через mDNS каждый раз заново.

## 2026-08-21, продолжение — Wi-Fi на wlan0 настроен (запасной канал на случай проблем с Ethernet)

Отвлеклись от k3s на Wi-Fi — юзер захотел иметь запасной канал связи с Pi на случай проблем с Ethernet/роутером.

### Wi-Fi модуль был отключён на уровне device tree

`wlan0` вообще не появлялся в `ip link`/`ip addr` — не просто не настроен, а физически не инициализировался. Причина — `/boot/firmware/config.txt:91` содержал `dtoverlay=disable-wifi` (дефолт DietPi-образа, встроенный Wi-Fi Pi 3B+ выключен из коробки). Закомментировали строку, перезагрузили — `wlan0` появился, `brcmfmac43455-sdio` загрузился штатно (`brcmfmac: brcmf_c_preinit_dcmds: Firmware: BCM4345/6 ... version 7.45.265`).

Важно: реальный файл — `/boot/firmware/config.txt`, не `/boot/config.txt` (последнего просто не существует на этой сборке DietPi/Trixie).

### CPU 61°C при загрузке — не проблема

DietPi motd после ребута показал `CPU temp: 61°C: Running hot, not recommended` (жёлтым). Проверили `vcgencmd get_throttled` → `0x80000` — это только бит "soft temperature limit was reached" (исторический, разово после ребута), биты активного throttling/undervoltage (0-3) чистые. `measure_temp` тут же показал 58.5°C. Не блокер, но стоит поставить радиатор на будущее под sustained k3s-нагрузку.

### Пароль Wi-Fi достали с ноута юзера, а не спрашивали вслепую

Ноут юзера уже был подключён к `TP-Link_9E48_5G` (Arch, `iwd` в качестве backend, TUI `impala` поверх). Пароль вытащили штатно: `sudo cat "/var/lib/iwd/TP-Link_9E48_5G.psk"` → `Passphrase=42121114`.

**Побочный инцидент — pam_faillock lockout.** До этого агент дважды по ошибке попытался выполнить `sudo cat ...` сам через свой Bash-тул (в т.ч. один раз перепутав `!`-префикс, который выполняется в терминале юзера, с обычным вызовом Bash-тула) — обе попытки провалились без реального ввода пароля, но **засчитались как невалидные попытки аутентификации** в `pam_faillock`. Дефолты `/etc/security/faillock.conf` (файл пустой, т.е. `deny=3`, `unlock_time=600`) — юзер после этого не мог зайти в sudo даже с верным паролем ("neverbeen wrong" — три подряд отказа). Диагностировали через `faillock` (без sudo, показывает собственный tally): 3 записи `SVC sudo V` за минуту. Решение — просто подождать 10 минут до автоматического снятия блокировки (сброс вручную через `faillock --reset` сам требует sudo, замкнутый круг). Сохранено в память: **агенту больше никогда не трогать sudo** — ни выполнять самому, ни пытаться ввести пароль; только сообщать юзеру команду.

### Применение Wi-Fi конфига на Pi

- DietPi Wi-Fi конфиг читается из `/boot/dietpi-wifi.txt` — **не** `/boot/firmware/dietpi-wifi.txt` (это два разных файла на разных точках монтирования; какой реально используется, подтвердили через `grep dietpi-wifi.txt /boot/dietpi/func/dietpi-wifidb`).
- Прописали `aWIFI_SSID[0]='TP-Link_9E48_5G'`, `aWIFI_KEY[0]='42121114'` (KEYMGR уже был `WPA-PSK` по умолчанию), применили через `/boot/dietpi/func/dietpi-wifidb 1` — переносит файл в `/var/lib/dietpi/dietpi-wifi.db` и генерирует `/etc/wpa_supplicant/wpa_supplicant.conf`.
- В `/etc/network/interfaces` секция `wlan0` уже была (шаблон DietPi), но `allow-hotplug wlan0` был закомментирован — из-за этого интерфейс не поднимался бы автоматически. Раскомментировали, подняли вручную `ifup wlan0` → DHCP выдал `192.168.0.213` с того же роутера, что и eth0 (`192.168.0.118`). `networking.service` в автозагрузке — конфиг переживёт перезагрузку.
- Оба интерфейса (`eth0`+`wlan0`) сейчас активны одновременно, дефолтный маршрут — через `eth0` (обычный приоритет ifupdown).

### Проверка отказоустойчивости — не до конца чисто

Юзер отключил Ethernet-кабель, включил обратно, попытался переподключиться по `ssh pi` — несколько раз подряd получил `Connection refused` на `dietpi.local`. На тот момент `avahi-resolve -n dietpi.local` отдавал `192.168.0.213` (адрес wlan0), т.е. mDNS переключился на Wi-Fi-адрес, но порт 22 туда не отвечал (не успели доразобраться — юзер прервал диагностику, переподключился с N-й попытки сам, сказал "все окей"). **Не выяснили до конца, что там произошло** — не стали копать глубже, юзер решил проблему сам, но это на заметку: если снова словим `Connection refused` через mDNS-имя после переключения интерфейсов — сначала проверить, что `sshd` слушает на актуальном адресе wlan0, и не путаница ли это с IPv6 link-local (был похожий баг с `DietPi.local`→IPv6 19-го числа, обошли через `AddressFamily inet` в `~/.ssh/config.d/personal.conf` — возможно там же и корень).
