# 2026-09-26 — планирование архитектуры session-app (cookie/account сервис)

## Контекст

Юзер накидал черновой флоу для нового сервиса: скачивание с площадок, требующих куки/аккаунт
(например SoundCloud — самый нижний пункт в `docs/agents/planning.md`, теперь стало ясно почему
именно нижний — зависимость от этого недостающего сервиса). Попросил оценку архитектуры, разбор
дыр, правильные вопросы — без кода, чисто дизайн-сессия.

## Разбор черновика — ключевые дыры, найденные в ревью

- Черновик вводил новые статусы очереди (`pending.cookie`, `pending.account`) — смешение стадии
  жизненного цикла джобы с причиной блокировки. В коде уже есть готовый паттерн под это:
  `BlockReason` enum + `requeueByBlockReason` (сейчас используется для `geo`/`PROXY`,
  `domain/block-reason.ts`, `application/requeue-blocked-jobs.ts`).
- Не было predела попыток/terminal-состояния для cookie-flow — риск бесконечного цикла
  pending → needs_cookie → pending.
- Не было дедупа: N ресурсов одного сервиса разом упёрлись в отсутствие куки → N параллельных
  запросов на логин к стороннему сервису (риск капчи/бана).
- Классификация ошибки ("протухла кука" vs "не подходит" vs "сервис недоступен") не была
  инкапсулирована и не различалась.
- Была путаница, к какому слою относится оркестрация — `deliver-job` (стадия 2, работает с уже
  скачанным файлом) явно не то место; это часть resolve-этапа `download-job` (стадия 1).
- Хранение куки ("текстовый блоб") — без обсуждения шифрования/redaction, при том что у проекта
  уже был прецедент утечки секрета в логах (`docs/diary/2026-09-26_token-in-logs-and-polling-crash.md`,
  тот же день, другая сессия).
- Proxy упомянут вскользь, без модели (один прокси на сервис? на аккаунт?).
- Межсервисная коммуникация (SQLite-очередь vs брокер) не была зафиксирована явно.

Разбор yt-dlp GitHub issues по ходу диалога подтвердил: у yt-dlp есть один надёжный сигнал именно
протухшей/ротированной куки (явный текст "cookies are no longer valid"), но `403`/"Sign in to
confirm you're not a bot" не различают причину — матчить их как "нужна новая кука" рискует крутить
рефреш вечно там, где он не поможет.

## Решения, принятые в диалоге

- Не вводим новые статусы очереди — переиспользуем `BlockReason` (`needs_cookie`, `account_banned`)
  + существующий `requeueByBlockReason`.
- Ресурсная джоба не имеет своего счётчика попыток на cookie-flow — висит `failed`/`needs_cookie`
  без ограничения, разблокируется реквью-триггером. Предел попыток — на **аккаунте**, не на
  ресурсе: отдельная джоба/очередь (`account_job`) со своим `MAX_RETRIES`; исчерпан → `account.status
  = banned` (terminal).
- Дедуп через атомарный conditional update `account.status: active → refreshing` перед созданием
  `account_job` (по образцу `requeueByBlockReason`).
- Несколько аккаунтов на сервис, с ротацией — стратегия выбора не решена (открытый вопрос), но
  сама логика ротации — зона ответственности session-service, не core.
- Proxy 1:1 с account, `UNIQUE(service_id, proxy_id)` — один прокси не может стоять за двумя
  аккаунтами одного сервиса (корреляция по IP), но может переиспользоваться между разными сервисами.
- Получение куки — через сторонний браузер-эмулятор (логин-автоматизация не пишется in-house).
- Хранение — `app.db`/SQLite (не S3: блоб маленький, self-host S3 на Pi, который и так на
  пределе ресурсов, — второй stateful-сервис ценой сопоставимой с прямым шифрованием, без реальной
  выгоды при self-host). Шифрование на уровне приложения, ключ из env (по образцу `BOT_TOKEN`),
  расшифрованное значение через `registerSecret` (`redact.ts`).
- Коммуникация core ↔ session-service — только через общую SQLite-очередь, никаких прямых вызовов
  между репозиториями/API. Сейчас — модуль в одном приложении, явная граница на будущее
  выделение в отдельный деплой.
- Pre-flight проверка "нужны ли ресурсу куки" — в resolve-этапе `download-job`, до попытки
  скачивания (не в `deliver-job`).

Всё зафиксировано в `docs/specs/session-app.specs.md` (переписан с нуля, старое содержимое сведено
в раздел "черновой флоу" как контекст).

## Открытые вопросы (не решены, специально)

- Проксирование скачивания: привязано к session-service или нет? Можно ли проксировать каждый
  запрос отдельно, или прокси — на весь процесс yt-dlp (один флаг)?
- Стратегия ротации аккаунтов (round-robin / LRU / случайный) — не выбрана.
- Различение "сторонний вендор временно не смог" vs "аккаунт реально забанен площадкой" —
  зависит от выбора конкретного браузер-эмулятора, решать при выборе вендора.
- Различение "кука протухла" vs "кука в принципе не подходит" по тексту ошибки yt-dlp — частично
  прояснено (см. выше), но решение отложено до реализации.
- Новое, всплывшее при формулировке шифрования: расшифровка нужна в процессе, который реально
  запускает yt-dlp (core) — значит core должен иметь тот же ключ, что и session-service. Пока один
  модуль/общий env — не проблема, при будущем разделении на отдельные деплои это станет вопросом
  распространения секрета между сервисами.
- Формат передачи куки в yt-dlp: `--cookies` ждёт файл на диске, не строку — кто материализует
  временный расшифрованный файл (`TMP_DIR`?) и гарантирует его удаление после вызова — не описано.

Все инфраструктурные открытые моменты — сознательное решение юзера **не закрывать их сейчас**:
в следующей итерации либо заглушки, либо не реализовывать вовсе, пока не понадобится.
