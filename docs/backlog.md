## fs-only cache-hit не переиспользуется (нет `deliver`)

Реализовано в сессии 2026-08-24 (ворктри `agent-aab999315a92a7e92`): `fs-cache-adapter.ts`
(`TrackStorePort`) вынес инлайновый `fs`-код из `application/process-download-job.ts` —
`stores: TrackStorePort[]`, фанаут `save()` по всем, `deliver()` вызывается только у
сторов, которые его реализуют (`isTrackCachePort`, duck-typing). Подробности и полный ход
решения — `docs/diary/2026-08-23_infra-restructure-plan.md`, секция «Ревизия — 2026-08-24».

**Остался один открытый хвост**: `findAndDeliver()` в application проверяет на cache-hit
только сторы, у которых есть `deliver` (сейчас — только telegram). fs-стор физически не
может сам раздать файл (доставка всё равно через Telegram), поэтому его `find()` в этой
проверке не участвует — он написан и рабочий (используется в момент `save()`, дедуп на
уровне "уже лежит на диске" не проверяется). **Следствие**: если `CACHE_TO_CHANNEL=false`
(только fs-архив, без telegram-кэша), повторный запрос того же трека **скачает его
заново** — эффективность, не корректность. Чтобы использовать fs-only хиты, нужно
расширить `NotifierPort` методом "отправить уже лежащий на диске файл" (переиспользовать
`sendMedia`-путь из `notify()`, сейчас завязанный на `DownloadResult`).

Не блокирует — сценарий с выключенным `CACHE_TO_CHANNEL` не является дефолтным.

## Контейнеризовать прокси-цепочку для обхода блокировки Telegram API

Сейчас (сессия 2026-08-23) обход блокировки `api.telegram.org` с домашней сети сделан **вручную на хосте** `dietpi` — SSH-туннель (`timeweb-socks5.service`) + `privoxy`-мост (SOCKS5→HTTP), оба systemd-юнитами прямо на Pi, не в GitOps. Подробности — `infrastructure/docs/k3s-flux-bootstrap.md`, раздел "Обход блокировки Telegram API" в Фазе 5.

**Почему цепочка именно такая** (не просто SOCKS5): связка `Telegraf`→`node-fetch`→кастомный `http.Agent` (`socks-proxy-agent`) не работает под Bun — запрос через SOCKS5-агент зависает навсегда без ошибки. `HttpsProxyAgent` (HTTP CONNECT) сработал. SSH сам HTTP не умеет (только SOCKS через `-D`), отсюда мост `privoxy`.

**Задача на потом** — перенести это в `infrastructure`-репозиторий как нормальный GitOps-компонент:
- Один общий Docker-образ (`debian-slim` + `apt-get install openssh-client privoxy`), публикуется через свою CI прямо в `infrastructure`-репозитории (`images/telegram-proxy/Dockerfile` + отдельный workflow)
- Один `Pod` с двумя контейнерами из этого образа (общий network namespace → общаются через `localhost`, не нужен `0.0.0.0`-костыль, которым обходили изоляцию хост/под): `ssh -N -D` в одном, `privoxy` в другом
- `Service` перед подом — стабильный DNS вместо IP ноды в `PROXY`
- SSH-ключ — `Secret` + volume-mount, не в образе

Цель — чтобы разворачивание на новом хосте не требовало ручного `apt-get`/`sed`/systemd на самой машине, а сводилось к применению манифестов + один секрет с SSH-ключом под нужный VPS-выход.

Не блокирует текущий деплой — рабочий стопгэп на хосте уже есть и протестирован (`curl` через `privoxy` → Telegram отвечает `302`).

## Разделить "скачивание" и "отправку в Telegram" на разные события очереди

Обнаружено в сессии 2026-08-23 при первом сквозном тесте (после починки прокси, см. `infrastructure/docs/diary/2026-08-23_kanalveschaniya-flux-deploy.md`): трек (4.2MB) успешно скачался, но аплоад в канал упал (`socket connection was closed unexpectedly` — обрыв на стриминге большого multipart-тела через прокси-туннель). Воркер (`src/worker/index.ts`) на ретрае **перекачал трек заново**, хотя файл на диске уже был — сейчас download и upload это один джоб в общей очереди, один retry-цикл на оба шага.

Правильно — развести на два независимых события:
- `download` — скачать источник → сохранить в `content/` (или временный стейдж)
- `send`/`upload` — взять уже скачанный файл → отправить в Telegram (канал + форвард юзеру)

У них разные failure-домены (источник/`yt-dlp` vs Telegram API/прокси) и должны быть разные retry-политики/бэкоффы. Ретрай `send` не должен трогать `download`.

**Согласуется с архитектурой из `docs/diary/2026-08-22_clean-architecture-refactor.md`**: отправка в Telegram — специфичная для Telegram функция (`NotifierPort`, реализуется в `infra/telegram`). Следуя этому же принципу, сама очередь/событие/ретрай для `send`-шага тоже должны быть определены **внутри `infra/telegram`**, а не в общем `application`/queue-worker слое — общий слой не должен знать про Telegram-специфичные детали ретраев (лимиты API, размер файла, таймауты прокси). Общий `queue-poller`/domain отвечает только за `download`; передача результата на отправку — уже зона ответственности telegram-инфры (свой воркер/очередь поверх `NotifierPort`, либо отдельная таблица `telegram_send_queue` по аналогии с `telegram_reply_refs`).

Не блокирует немедленно (ретраи хоть и неэффективны, но система в итоге доезжает), но стоит сделать до рефакторинга каталогов под `domain/application/infra` — это прямо влияет на схему `queue`/`queue-item`.

## Быстрый отказ для DRM-защищённых треков (без 3 попыток)

Обнаружено в сессии 2026-08-23 при тесте плейлиста из 9 треков (SoundCloud, Erik Satie — Gymnopédies/Gnossiennes, официальные загрузки). Все 9 треков упали на `yt-dlp` с одной и той же причиной:

```
[soundcloud] 1166805070: Downloading hls_mp3 format info JSON
WARNING: [soundcloud] 1166805070: hls_mp3 format not found
[soundcloud] 1166805070: Downloading http_mp3 format info JSON
WARNING: [soundcloud] 1166805070: http_mp3 format not found
ERROR: [soundcloud] 1166805070: This video is DRM protected
```

Это не баг — SoundCloud реально защищает часть контента (обычно официальные/монетизированные Go+ загрузки) DRM'ом, `yt-dlp` физически не может это скачать ни при каких сетевых настройках. Прокси/Bun/аплоад тут ни при чём — цепочка (прокси → скачивание → буфер → `fetch`-аплоад), уже проверенная и рабочая на обычных треках, до аплоада даже не доходит.

**Проблема** — очередь (`src/worker/index.ts`) не отличает эту постоянную (permanent) ошибку от временной. `isGeoBlocked`/`isNotFound` уже есть как fast-fail хелперы (уходят в `failed`/`geo_blocked` сразу), а DRM-ошибка попадает в общую ветку `else` — тратит все 3 попытки с экспоненциальным бэкоффом (30с+60с+120с ≈ 3.5 мин) прежде чем сдаться. На плейлисте из 9 таких треков (concurrency=1, всё последовательно) это набежало в сумме на ощутимое время впустую.

**Фикс на потом** — добавить `isDrmProtected(error)` по аналогии с `isGeoBlocked`/`isNotFound` (паттерн на `"DRM protected"` в тексте ошибки `yt-dlp`), заводить сразу в `status = 'failed'` без ретраев, с понятным сообщением юзеру (сейчас на любой exhausted-провал шлётся общее "превышено число попыток" — для DRM стоит явно написать "трек защищён DRM, скачивание невозможно", а не намекать что можно как-то дожать ретраями).

Не блокирует — очередь и так корректно завершает джобу как `failed` после 3 попыток и не зацикливается, просто неэффективно тратит время. Плейлист-механизм (веерное разбиение на джобы, дедуп по кэшу) сам по себе не проверен на не-DRM контенте — это отдельно, надо перепроверить на плейлисте без официальных/монетизированных треков.

## `blockReason` — общий словарь строк без единого типа

Найдено в ревью 2026-08-24 (заметка на `formatFailureMessage()` в
`infra/adapters/telegram-notifier.ts`: "is it error from yt-dlp adapter constants?").
`DownloadResult.blockReason` (`domain/download.ts`) типизирован как обычный `string?` —
намеренно opaque для domain/application (см. `docs/specs/types.md`). Но фактически у него
два независимых производителя и один потребитель, ничем на уровне типов не связанные:

- `infra/adapters/yt-dlp.ts` пишет `"geo"` / `"drm"`
- `application/process-download-job.ts` пишет `"too_large"` (проверка размера файла **после**
  успешного скачивания — не yt-dlp-адаптер, вопреки заметке)
- `infra/adapters/telegram-notifier.ts` (`formatFailureMessage`) сравнивает результат со
  всеми тремя литералами вручную (`=== "geo"`, `=== "drm"`, `=== "too_large"`)

Опечатка в любом из трёх мест (например `"too_large"` vs `"too-large"`) не поймается
компилятором — просто молча выпадет в дефолтную ветку сообщения ("превышено число
попыток") вместо специфичного текста. Три места физически разнесены по разным файлам,
искать все точки записи/сравнения при правке приходится вручную.

**Фикс** — завести общий `type BlockReason = "geo" | "drm" | "too_large"` (не в
`domain/download.ts`, чтобы не тянуть инфра-семантику в domain — например рядом,
в `infra/adapters/` или отдельным shared-файлом типов для инфры) и использовать его во
всех трёх местах вместо голого `string`. Дёшево, не меняет поведение, снимает риск молчаливого
рассинхрона. Не блокирует — сейчас все три строки совпадают.

## `NotifierPort.notify` / `TrackCachePort.deliver` — пересечение ответственности

Зафиксировано как открытый вопрос ещё в `docs/diary/2026-08-23_infra-restructure-plan.md`
(секция "Ревизия — 2026-08-24"), формализуется сюда, чтобы не потерялось. Оба метода
резолвят `jobId → chatId` через `telegram_reply_refs` и оба в итоге что-то отправляют
пользователю через Telegram Bot API:

- `NotifierPort.notify()` — свежескачанные байты через `sendMedia` (только когда
  `CACHE_TO_CHANNEL=false`, т.е. кэш выключен)
- `TrackCachePort.deliver()` — форвард уже существующего сообщения из канала через
  `forwardMessage` (на cache-hit, когда кэш включён)

Не полный дубль (разные API-вызовы, разные источники данных), но смысловое пересечение
("по jobId достать адрес и послать что-то в Telegram") есть — два порта, которые в
принципе могли бы быть одним с двумя реализациями метода "доставить результат". Решение
на сессии 2026-08-24 — **не трогать сейчас**, оставить как есть, порог сложности объединения
не оправдан текущим объёмом кода. Не блокирует. Пересматривать, если появится третий
похожий кейс "резолви jobId и пошли в Telegram" — тогда правило "трёх" оправдает абстракцию.

## Drizzle вместо ручного `bun:sqlite` + массив миграций — не сейчас, путь назад открыт

Вопрос поднят в ревью 2026-08-24 (заметки "why we dont use drizzle?" на
`infra/db/telegram-db.ts` и `infra/repository/queue-repository.ts`). Осознанный выбор,
унаследованный от кода до рефакторинга — `bun:sqlite` напрямую + ручной массив
`{name, sql}`-миграций (тот же паттерн, что был в `src/db/schema.ts`), ручной row-mapping
(`toQueueItem` и аналоги). Drizzle дал бы типобезопасную схему и `drizzle-kit`-миграции.
Решение — не мешать это в текущий рефакторинг: тот про слои (domain/application/infra), а
не про персистентность, и переход не чинит ни один текущий баг.

**Важно — не блокирует переход позже**: `drizzle-orm/bun-sqlite` — официальный драйвер,
оборачивает тот же `Database`-инстанс, который уже открывают `openAppDb()`/`openTelegramDb()`.
Путь миграции, когда понадобится:
1. `drizzle-kit introspect` на существующих `app.db`/`telegram.db` (в т.ч. на боевых данных
   с Pi) — генерит `schema.ts`, соответствующий текущим таблицам, как "нулевой" снапшот
2. Дальнейшие изменения схемы — уже через `drizzle-kit generate` от этого снапшота
3. Замена реализации происходит **только** внутри `infra/repository/*.ts` — контракты портов
   в `domain/` (`QueueRepository`, `ResourceRepository` и т.д.) не меняются ни на строчку

Т.е. это чисто внутренняя замена одного infra-слоя, без данных-миграции и без риска для
domain/application. Откладывать сейчас — не значит терять возможность сделать это позже
дешевле.

**Уточнение из ревью 2026-08-24** (заметка в коммите `899b06b`, `chore(common): review
comments`, на `bot.start()`-строке в `telegram-handlers.ts`: "mv all messages to
telegram.localization.json"): цель — **не** i18n/мультиязычность, а единая точка контроля —
чтобы всё, что уходит пользователю, было видно и правилось из одного файла, без
необходимости помнить, что часть строк живёт в `telegram-handlers.ts`, а часть в
`telegram-notifier.ts`. Конкретно предлагается: `messages.ts` (константы/функции для
параметризованных строк вроде `notifyPlaylistQueued`) в `infra/presentation/`, импортируется
обоими файлами. Механическая правка, не архитектурная — можно делать одновременно с
собственно правкой текстов выше, отдельным заходом после мёржа.

## Изолировать сторы друг от друга в process-download-job

Найдено в сессии 2026-08-24 на живом прогоне: бот не был добавлен в канал → `channel.save()` упал (`Bad Request: chat not found`) прямо на первой строке (аплоад), **до** `trackRefs.save()`/`resource.save()`. Цикл в `runJob` (`process-download-job.ts`) перебирает сторы последовательно и не ловит ошибку на уровне отдельного стора — исключение прервало весь `for`, до второго стора (`fs`, локальный архив в `CONTENT_DIR`) дело не дошло. В итоге упавший канал заблокировал независимый архивный бэкенд, хотя формально они друг от друга не зависят.

Фикс — обернуть `save()`/`deliver()` каждого стора в try/catch **внутри** цикла:
- ошибка одного стора не должна прерывать остальные (fs всё равно должен сохранить архив, даже если канал недоступен)
- копить ошибки, после цикла — если хоть одна была — перебросить наверх, чтобы сработала существующая retry-логика (`backoff`/`exhausted`/`error_log`)
- `deliver()` стора звать только если его же `save()` прошёл успешно
- `delivered` считать по фактически успешным `deliver()`, а не по факту вызова

Не требует отдельных очередей на стор — job как единица ретрая (`pending`/`retry_after`/`retries`) остаётся одна, `fs.save()` идемпотентен (`copyFile` перетирает), повторный вызов на ретрае безвреден. Оценка — некрупная правка, один цикл в `process-download-job.ts`.

Не решает соседнюю проблему (повторное скачивание при ретрае, см. пункт выше "Разделить скачивание и отправку") — эта правка про независимость сторов друг от друга, а не про переиспользование уже скачанного файла между попытками.

## Почистить мусор в queue: stale error, непубликуемый track_id

Найдено в сессии 2026-08-24 при сверке по БД после успешного ретрая job 1 (Ruchey):

- `updateStatus(id, "done")` в `process-download-job.ts` вызывается без `patch` — поле `queue.error` не чистится и остаётся текстом ошибки от предыдущей (упавшей) попытки, даже когда job в итоге дошёл до `done`. Не user-facing (`/status` отдаёт только счётчики по статусам, не читает `error`), но вводит в заблуждение при прямом чтении БД.
- `queue.track_id` у job 1 в БД — `NULL`, хотя трек успешно закэширован (`resource`/`telegram_track_refs` заполнены). `runJob` резолвит `trackId` через `downloader.getInfo(url)` в локальную переменную и никогда не пишет его обратно в `queue` (`updateStatus` в `queue-repository.ts` вообще не принимает `trackId` в патче). На каждом ретрае того же job'а `getInfo()` дергается заново — лишний (хоть и дешёвый, metadata-only) вызов yt-dlp вместо переиспользования уже известного `trackId`.

Fix — при успешном `done` явно чистить `error`/`block_reason` (`patch: { error: null, blockReason: null }`); при первом резолве `trackId` — сразу писать его в `queue.track_id` (добавить `trackId` в `Partial<QueueItem>` для `updateStatus`, звать сразу после `getInfo()` в `runJob`).

Важно: это НЕ причина повторного полного скачивания трека при ретрае (см. "Разделить скачивание и отправку") — та проблема из-за того, что при первом падении ни один стор не успел сохранить трек целиком, `findDeliverable` ищет по `resource`/`telegram_track_refs`, а не по `queue.track_id`. Этот пункт — только про мусор в самой строке `queue` и лишний `getInfo()`-вызов.
