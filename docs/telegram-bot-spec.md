# Telegram Bot — спецификация хендлеров

Список хендлеров бота и их место в clean-архитектуре (`domain`/`application`/`infra`,
см. `docs/diagram.d2` и `docs/diary/2026-08-22_clean-architecture-refactor.md`).

## Хендлеры

### `handle-message` (presentation, `infra/presentation/telegram-bot`)

Обычное сообщение боту в личке со ссылкой.

- Извлечь URL из текста (валидация — общая чистая функция, переиспользуется
  `listen-channel`, не дублируется)
- → `EnqueueDownload` (application) с reply-target = `{ chatId: юзера, messageId: сообщения }`

Отдельно от него — command-хендлеры `/start`, `/status` (не generic message, а
`bot.command(...)`).

### notify (не хендлер — завершение `process-download`)

После скачивания трека: пост в основной канал → reply файлом на исходное
сообщение (тому, кто запросил). Reply-target обобщён (`{chatId, messageId}`),
работает одинаково для запроса из личного чата и из канала (см. `listen-channel`) —
отдельного хендлера под это не требуется, это часть `NotifierPort`, вызываемого
из `process-download`.

### `listen-channel` (presentation, admin-only команда-переключатель)

Включает листенер на приватном канале.

- **Auth**: только админ/владелец может вызвать команду
- Слушает `channel_post`
- Фильтр: пропускать сообщения с непустым `reply_to_message` (в приватном канале
  реплаит только бот — так исключаются собственные ответы-файлы бота, даже если
  в caption вдруг продублирована исходная ссылка)
- На валидную ссылку → та же `EnqueueDownload`, reply-target = `{chatId: канала,
  messageId: поста}`

### `handle-channel-history` (presentation, admin-only команда) — **заглушка**

Задумывался как бэкафилл: пройтись по истории канала, найти ещё не отвеченные
ссылки, докачать. **Не реализуем** — Telegram Bot API не даёт получить историю
чата/канала (`getChatHistory` в Bot API не существует), только real-time апдейты
через `channel_post`. Для полноценной реализации нужен MTProto-клиент
(userbot, gramjs/mtcute, отдельная авторизация по номеру телефона) — вне текущего
scope (проект использует только `telegraf`/Bot API).

Команда должна существовать и отвечать заглушкой, например:

```
Пока не реализовано — нужен MTProto-клиент (userbot) для чтения истории канала.
```

## Идемпотентность (на будущее, если `handle-channel-history` всё же будет реализован)

Не полагаться на локальную БД как источник истины "уже отвечено". Сообщение со
ссылкой считать обработанным, если в канале **есть** сообщение с
`reply_to_message_id`, равным его id:

- файл удалили из канала вручную → реплая с этим id больше нет → следующий проход
  перекачивает и отправляет заново
- локальная БД (`queue`, `telegram_reply_refs`) — только для дедупа *внутри*
  очереди (не поставить в очередь то, что уже `pending`/`processing`,
  см. `planning.md` п.11), с этой проверкой не пересекается
