# Cookies для yt-dlp (SoundCloud-авторизация)

Отдельная заметка, не общая секция — фича сложная (несколько движущихся
частей: код, secret-менеджмент в k8s, операционный процесс ре-экспорта) и важная
(без неё часть SoundCloud-треков вообще не скачивается). **Пока не зафиксировано**
в `docs/diagram.d2`/`docs/specs/types.md` — по просьбе, там ничего не трогаем,
пока фича не близка к реализации.

## Проблема

yt-dlp на SoundCloud для части треков не может получить рабочий URL потока —
запрос "format info JSON" (`hls_mp3`/`http_mp3`) возвращает "not found" вообще,
а не урезанный 30-секундный превью. Локальный тест подтвердил: с валидными куки
браузера (залогиненный аккаунт, не обязательно платный Go+) запрос проходит и
трек скачивается полностью. Без куки — SoundCloud не отдаёт ссылку на поток вовсе.

Подтверждено официальным issue yt-dlp
([#8390](https://github.com/yt-dlp/yt-dlp/issues/8390)) — мейнтейнеры сами
обсуждают эту же симптоматику, причина на стороне SoundCloud (авторизация),
не баг yt-dlp.

## Технический контекст

Два способа передать куки в yt-dlp:

- `--cookies-from-browser BROWSER[:PROFILE]` — тянет куки прямо из установленного
  браузера. **Не подходит** — бот работает headless в контейнере, браузера там нет.
- `--cookies FILE` — читает заранее экспортированный файл в формате Netscape.
  Единственный вариант для headless/Docker.

Важные оговорки из доков yt-dlp:

- Файл куки может содержать чувствительные данные (сессионные токены) — прокидывать
  как отдельный **k8s Secret + volume-mount** (файл, не переменная окружения), тем же
  паттерном что уже в бэклоге для `BOT_TOKEN`/SOPS. Манифесты — в отдельном
  репозитории `infrastructure`, здесь только код/контракт.
- Сессионные куки SoundCloud не вечные — периодически придётся **вручную
  ре-экспортировать** заново. Разовая, но повторяющаяся операционная задача, не
  автоматизируется без реализации логина от имени бота (вне scope).

## Архитектурное направление (обсуждено, не зафиксировано в коде/схеме)

Новый domain-репозиторий (`Repository`, не `Port` — просто хранение blob'а по ключу,
без взаимодействия с внешней системой, см. рассуждение в `docs/specs/types.md` про
`TrackCachePort`):

```ts
interface CookieRepository {
  findByUserId(userId: number): Promise<string | null>; // путь к файлу куки или null
  save(userId: number, content: Buffer): Promise<void>;  // upsert
}
```

- Реализация — `infra/fs/cookie-repository.ts`, файлы на диске (`data/cookies/<userId>.txt`
  или рядом с `CONTENT_DIR`). Не telegram-специфично, несмотря на источник данных —
  Telegram тут только канал доставки файла, репозиторий про это не знает.
- `DownloaderPort.getInfo`/`download` получают доп. опциональный параметр `cookiesPath`.
- Развилка "дать `--cookies` или нет" — целиком внутри `infra/downloader/yt-dlp`
  (`downloader.ts`), тем же паттерном, что уже есть для `--proxy`:
  ```ts
  const cookieArgs = cookiesPath ? ["--cookies", cookiesPath] : [];
  ```
- `ProcessDownloadJob` перед вызовом `downloader.download()` сам спрашивает
  `cookieRepo.findByUserId(job.userId)` и прокидывает результат — обычная
  оркестрация двух портов внутри use-case, ничего нового по форме.

## Что нужно реализовать

- [ ] `CookieRepository` (domain) + fs-реализация (`infra/fs`)
- [ ] `DownloaderPort.getInfo`/`download` — доп. параметр `cookiesPath`
- [ ] `downloader.ts` — условный `--cookies` флаг, аналогично `--proxy`
- [ ] **Telegram-хендлер приёма файла** — `bot.on(message("document"), ...)`:
      скачать файл через `ctx.telegram.getFileLink()`, сохранить через
      `cookieRepo.save(ctx.from.id, content)`. Без отдельного use-case — прямой
      вызов репозитория из presentation (нет бизнес-логики поверх, тот же принцип,
      по которому не заводили entity-слой)
- [ ] `ProcessDownloadJob` — lookup куки перед `download()`
- [ ] k8s Secret + volume-mount под файл куки — работа в репозитории `infrastructure`
      (не здесь), после того как код готов принимать путь к файлу

## Открытый вопрос: удобный экспорт куки, желательно с телефона

Сейчас единственный проверенный способ — desktop-браузер + расширение
("Get cookies.txt LOCALLY" или аналог) или `yt-dlp --cookies-from-browser chrome
--cookies cookies.txt <url>` локально, затем файл руками отправляется боту в Telegram.

Для мобильного браузера есть жёсткое техническое ограничение: сессионные
куки авторизации почти наверняка помечены `HttpOnly` — это значит, их **нельзя**
прочитать через `document.cookie` в JS, то есть букмарклет (JS-код в закладке,
работающий без установки расширения) технически не сработает для этого конкретного
случая, независимо от платформы. Экспорт куки такого типа возможен только через
браузерное расширение с доступом к привилегированному `chrome.cookies` API
(или аналогу), а не через обычный JS на странице.

Практические варианты требуют отдельного ресёрча:

- **Android** — браузеры с поддержкой Chrome-расширений (Kiwi Browser, возможно
  Firefox for Android с ограниченным набором расширений с addons.mozilla.org) —
  под вопросом, актуальность расширений меняется, нужно проверить на месте.
- **iOS** — по факту нет пути через расширения без джейлбрейка; Safari Web
  Extensions через App Store — маловероятно найти готовое под эту задачу.
  Реалистичный вариант — экспорт на десктопе один раз, дальше файл просто
  форвардится боту с телефона через Telegram (Saved Messages / облако) — не
  "с телефона" в смысле экспорта, но комфортно в смысле доставки.
- Не рассматривали: временный extension/companion-скрипт под задачу — отдельная
  небольшая эксплуатационная утилита, вне scope самого бота.

Решение пока не принято — фиксируется как открытый вопрос для будущего ресёрча,
не блокирует реализацию основного пути (desktop-экспорт → Telegram-загрузка).
