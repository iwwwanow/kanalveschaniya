# Где живут порты: все в `domain/` — пересмотреть

Сейчас все порты лежат в `src/domain/`: репозитории (`QueueRepository`, `ErrorLogRepository`) и внешние сервисы (`DownloaderPort`, `NotifierPort`, `ResourceStorePort`, `DeliveryPort`). В `application/` только use-case'ы и их input/result-типы, единственное исключение — `WorkerLog` (`application/worker-log.ts`). Это осознанная модель «domain = контракты ядра, application = только оркестрация» (подробности — `docs/diary/2026-08-22_clean-architecture-refactor.md`). Модель корректна: зависимости направлены внутрь.

Есть ещё два общепринятых варианта:

- **Clean у Мартина.** Порты лежат в слое use case'ов. Это DIP: интерфейс принадлежит тому, кто его вызывает, а вызывает use case. На схеме Мартина «Data Access Interface» нарисован в круге use case'ов, а в entities — только бизнес-правила без I/O.
- **DDD у Эванса/Вернона.** Репозитории лежат в domain, потому что они часть модели («коллекция агрегатов»). Порты к внешнему миру (уведомления, внешние API) — в application.

Плюс текущей модели: driven-адаптеры (`infrastructure/repository/*`, `infrastructure/adapters/*`) зависят только от `domain`, `application` им не нужен. Минус: в domain попадают контракты, форма которых продиктована сценариями, а не бизнесом. Например, `NotifierPort.notifyPlaylistQueued` появился ради fan-out плейлиста, а `DeliveryPort` — ради Telegram-доставки. Тогда «domain» перестаёт означать «модель предметной области» и становится просто «всё, от чего зависит ядро». `WorkerLog` в `application/` выпадает из правила: по Мартину он лежит правильно, по текущей модели — нет.

Что нужно: разобраться, сделать раскладку чище и выбрать одно правило, которое объясняет положение каждого интерфейса без исключений. Перенести всё по Мартину или по Эвансу, либо оставить текущую модель и записать критерий в `CLAUDE.md`. Связано с `docs/backlog/2026-09-21_event-driven-core-redesign.md`: если `NotifierPort` сведётся к `handle(event)`, вопрос, чей это контракт, решается заодно. Та же раскладка переиспользуется в новом проекте (`iwwwanow_excurtion-aggregator-proto`), поэтому лучше прийти к одному правилу для обоих.
