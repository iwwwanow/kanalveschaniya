# Оформление бота (UX-текст) — юзер отредактирует сам

Отмечено в сессии 2026-08-23 (после реализации clean-architecture рефакторинга,
`docs/diary/2026-08-23_infra-restructure-plan.md`). Юзер хочет сам пройтись по
пользовательским текстам бота, не через агента — предметная правка после пуша
рефакторинга архитектуры. Не блокирует мёрдж `refactor/architecture`.

Что входит:
- Команды и их ответы — `/start`, `/status` (сейчас статичные строки в
  `infra/presentation/telegram-handlers.ts`)
- Тексты сообщений при постановке в очередь/дедупе/ошибках ("Добавлено в очередь",
  "Уже в очереди", сообщения об ошибках — `infra/adapters/telegram-notifier.ts`,
  `formatFailureMessage()`)
- Как бот постит в канал (сейчас — просто аплоад файла с caption, без доп. оформления)
- Подписи (caption) к трекам — сейчас `result.track.title` как есть, без форматирования/шаблона

Все эти строки после рефакторинга сосредоточены в `infra/presentation/`
(`telegram-handlers.ts`) и `infra/adapters/telegram-notifier.ts`/`telegram-channel-cache.ts`
(caption при аплоаде) — искать правки там.

**Уточнение из ревью 2026-08-24** (заметка в коммите `899b06b`, `chore(common): review
comments`, на `bot.start()`-строке в `telegram-handlers.ts`: "mv all messages to
telegram.localization.json"): цель — **не** i18n/мультиязычность, а единая точка контроля —
чтобы всё, что уходит пользователю, было видно и правилось из одного файла, без
необходимости помнить, что часть строк живёт в `telegram-handlers.ts`, а часть в
`telegram-notifier.ts`. Конкретно предлагается: `messages.ts` (константы/функции для
параметризованных строк вроде `notifyPlaylistQueued`) в `infra/presentation/`, импортируется
обоими файлами. Механическая правка, не архитектурная — можно делать одновременно с
собственно правкой текстов выше, отдельным заходом после мёржа.
