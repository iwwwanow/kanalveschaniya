### обзор

session-service (он же cookie-service) — сервис по авторизации, ротации аккаунтов, выгрузке куки и (частично) проксированию скачивания для ресурсов с сервисов, требующих авторизации.

Сейчас — модуль в этом же приложении (общая `app.db`), закладываем возможность выделения в отдельный деплой позже (см. «границы»).

### принятые решения

- **Не вводим новые статусы очереди** (`pending.cookie`/`pending.account`). Переиспользуем существующий механизм `BlockReason` + `requeueByBlockReason` (уже используется для `geo`/`PROXY`, см. `domain/block-reason.ts`, `application/requeue-blocked-jobs.ts`). Новые значения: `needs_cookie`, `account_banned` (terminal).
- **Ресурсная джоба (`queue`) не имеет собственного счётчика попыток на cookie-flow.** Падает в `failed` / `block_reason = needs_cookie` и висит без ограничения — ровно как `geo`-джобы висят до появления `PROXY`. Разблокируется реквью-триггером, когда для сервиса появляется рабочий аккаунт. Инфинит-луп исключён не таймаутом на ресурсе, а тем, что предел попыток — на аккаунте, не на ресурсе.
- **Попытка получить/обновить куки — отдельная джоба** (своя очередь/таблица `account_job`, привязана к `account_id`), со своим `status`/`retries`/`retry_after`/`MAX_RETRIES`. Дошла до `MAX_RETRIES` → `account.status = banned` (terminal). `backoffSeconds`/`MAX_RETRIES` (`domain/queue.ts`) — чистые функции без привязки к таблице, переиспользуются как есть; SQL-репозиторий у `account_job` свой (не единый generic-репозиторий на две разные таблицы — риск утечки абстракции).
- **Дедуп запроса на куки**: перед созданием `account_job` — условный update `account.status: active → refreshing` (`UPDATE ... WHERE status = 'active'`, по образцу `requeueByBlockReason`). Если 0 строк задето — обновление уже в процессе, повторное событие не создаём.
- **Несколько аккаунтов на сервис, с ротацией.** Стратегия выбора следующего аккаунта — открытый вопрos (см. ниже). Выбор аккаунта — задача session-service (только он знает `active`/`cooldown`/`banned` по всем аккаунтам сервиса); core не заботится, какой конкретно аккаунт стоит за выданной куки.
- **Proxy — 1:1 с account, с ограничением.** `account.proxy_id` → `proxy.id`. Constraint: `UNIQUE(service_id, proxy_id)` — один прокси не может быть у двух аккаунтов *одного* сервиса (иначе площадка коррелирует их по IP и банит вместе), но может быть переиспользован аккаунтами разных сервисов.
- **Получение куки — через сторонний браузер-эмулятор** (логин-автоматизация не пишется in-house). Различение "их временный сбой" vs "аккаунт реально забанен площадкой" по ответу вендора — вопрос выбора вендора, решается ближе к реализации (открытый вопрос ниже).
- **Хранение куки: в `app.db`/SQLite, не S3.** Куки-файл маленький (KB, не MB) — довод "большой блоб раздувает WAL" не применим. Шифрование — на уровне приложения, симметричный ключ из env (по образцу `BOT_TOKEN`), расшифрованное значение проходит `registerSecret` (`redact.ts`), чтобы никогда не попасть в логи/`error_log`. Self-hosted S3 (MinIO/Garage) отклонён: на Pi, который и так на пределе, это второй stateful-сервис (свой процесс, учётки, бэкап, порт) — операционная цена сопоставима с шифрованием блоба самостоятельно, а обещанная выгода (шифрование/IAM "бесплатно") при self-host не материализуется, потому что настраивать шифрование/доступ всё равно приходится самому. Managed S3 (R2/B2, free tier) — запасной вариант, если объём/размер куки вырастет на порядки.
- **Классификация ошибки "протухла кука" vs "не подходит" оставлена открытой** (см. ниже) — есть предварительное наблюдение по yt-dlp (см. диалог/бэклог), но решение отложено до реализации.
- **Межсервисная коммуникация: только через общую SQLite-очередь**, никаких прямых вызовов репозиториев/API между core и session-service — уже заложено с самого начала черновика, здесь фиксируется явно как граница. При будущем выделении session-service в отдельный деплой это должно означать замену адаптера (как читается/пишется очередь), а не переписывание логики.
- **`deliver-job` — не то место.** Проверка "нужны ли ресурсу куки" — часть resolve-этапа `download-job` (стадия 1, до попытки скачивания), не `deliver-job` (стадия 2, работает с уже скачанным файлом). Новый pre-flight-чек в resolve: `serviceRepo.findByUrl(url)` → если `service.requiresCookie && !hasUsableCookie(service)` → сразу `failJob(needs_cookie)`, не тратя попытку на заведомо обречённую загрузку.

### открытые вопросы

- **Прокси и скачивание**: должно ли проксирование самого скачивания быть привязано к этому сервису вообще? Можно ли проксировать каждый запрос отдельно, или мы проксируем не запрос, а весь процесс yt-dlp (как он вообще работает с прокси — один флаг на процесс)?
- **Стратегия ротации аккаунтов** внутри session-service: round-robin / least-recently-used / случайный выбор — не выбрано.
- **Различение "временный сбой вендора" vs "аккаунт забанен площадкой"** в ответе стороннего браузер-эмулятора — зависит от выбора вендора, решается ближе к реализации. Если вендор не даёт такого различения — весь трафик сбоев будет валиться в `banned` ошибочно.
- **Различение "кука протухла" vs "кука никогда не подходила" (аккаунт жив, но куки не спасают)** по сообщению об ошибке скачивания — решение отложено до реализации. Известно: у yt-dlp есть один надёжный сигнал ("The provided YouTube account cookies are no longer valid...", т.е. явная ротация), но `HTTP 403`/`Sign in to confirm you're not a bot` не различают причину (может быть и протухшая кука, и живой бан, и вовсе не связанная с куками бот-проверка, которую обновление куки не лечит).
- **Новый вопрос, всплывший при описании шифрования**: расшифровка куки нужна в процессе, который реально запускает yt-dlp (core, adapter), — значит core должен иметь тот же ключ шифрования, что и session-service. Пока это один модуль/общий env — не проблема; при будущем разделении на отдельные деплои это становится вопросом распространения секрета между двумя сервисами, а не только вопросом хранения. Не решено, куда это ляжет (shared secret store / core вообще не расшифровывает сам, а получает готовый файл от session-service через файловую систему?).
- **Формат передачи куки в yt-dlp**: `--cookies` ожидает файл на диске — значит расшифрованную куку придётся материализовать во временный файл (в `TMP_DIR`?) на время вызова subprocess и гарантированно удалить после. Не описано, кто это делает и с какой дисциплиной (аналог обращения с секретами в `redact.ts`, но для файлов, не для строк в логах).

### домен (черновой флоу — контекст, как пришли к решениям выше)

- делаем попытку скачивания
- если resource относится к сервису, который нужно скачивать по куки, и есть куки — то попытка скачивания
- если ресурс относится к сервису, который нужно скачивать по куки и куки нет — сразу `failed` / `needs_cookie`, без попытки скачивания (см. «принятые решения»)
- у resource есть url — по нему выставляется `service` при первой попытке скачивания. `Service 1—* Resource`
- cookie-service (session-service) ловит `needs_cookie`-события:
  - проверяет, есть ли уже в процессе создание куки/аккаунта для этого сервиса (дедуп через `account.status`, см. выше) — если есть, пропускает
  - иначе создаёт `account_job` на аккаунт (или ротирует на другой активный аккаунт)
  - по готовности — реквьюит заблокированные ресурсные джобы этого сервиса (`requeueByBlockReason`)
- ресурсная джоба при повторном claim читает актуальную куку из `account`/`cookie` таблиц напрямую (общая БД) — очередное событие не переносит сам блоб куки, только сигнал "можно повторить"

### сущности

- **service**: `id, name, url_pattern, requires_cookie: bool`
- **account**: `id, service_id, status: active | cooldown | banned, proxy_id`
- **proxy**: `id, ...`; `UNIQUE(service_id, proxy_id)` через `account`
- **cookie**: `id, account_id, blob_encrypted, created_at, last_used_at`
- **account_job**: попытка получить/обновить куки для `account_id`; свои `status/retries/retry_after`, независимые от ресурсной очереди

### application-use-cases (черновой список, не финал)

- `get-auth-context` / `find-usable-cookie(service)` — читает актуальную куку для сервиса (без знания, какой аккаунт за ней стоит)
- `establish-session` (`authenticate-account`) — запускает получение куки через браузер-эмулятор
- `refresh-session`, `revoke-session`, `rotate-proxy`
- `requeue-blocked-by-service(service_id)` — аналог существующего `requeue-blocked-jobs.ts`, но триггерится по готовности куки, а не по старту процесса

### db-tables (черновой список)

- `proxies`
- `accounts` (service_id, proxy_id, status)
- `cookies` (account_id, blob_encrypted, ...)
- `account_jobs` (account_id, status, retries, retry_after)
- `services` (url_pattern, requires_cookie)

### отложено (не в первой версии)

- proxy per-account как таргетируемая настройка (сейчас просто constraint в схеме, без UI/автоподбора)
- вендор-специфичная обработка бана/капчи — зависит от выбора стороннего браузер-эмулятора
- managed/self-host S3 для куки — не нужно на ожидаемых объёмах
- tg-bot-mention on chat to download track — не относится к session-service, отдельная фича core-бота
